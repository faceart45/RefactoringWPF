## Критические проблемы (нарушающие работу приложения)

### 1. DataGrid не отображает данные
- **Причина:** в классе `Order` использовались публичные поля вместо свойств.
- **Симптом:** таблица оставалась пустой, несмотря на добавленные заказы.
- **Выполненные изменения:** все публичные поля заменены на свойства с аксессорами `get` и `set`.
- **Обоснование:** WPF использует механизм отражения (reflection) для получения данных при привязке. DataGrid ищет публичные свойства, а не поля. Поля механизмом привязки не поддерживаются, поэтому таблица не могла прочитать данные.

### 2. Коллекция заказов не уведомляет UI об изменениях
- **Причина:** использовался `List<Order>` вместо `ObservableCollection<Order>`.
- **Симптом:** после добавления или удаления заказа таблица не обновлялась автоматически.
- **Выполненные изменения:** коллекция заменена на `ObservableCollection<Order>`.
- **Обоснование:** `ObservableCollection<T>` реализует интерфейс `INotifyCollectionChanged` и автоматически уведомляет DataGrid об изменениях. При вызове метода `Add` или `Remove` коллекция генерирует событие `CollectionChanged`, на которое подписан DataGrid, и перестраивает строки без ручного обновления.

### 3. Небезопасный ввод пользователя
- **Причина:** использовались `int.Parse` и `decimal.Parse` без `TryParse` и без обработки исключений.
- **Симптом:** при вводе буквы или пустой строки приложение завершало работу с необработанным исключением.
- **Выполненные изменения:** методы `Parse` заменены на `TryParse` с проверкой результата.
- **Обоснование:** `TryParse` не выбрасывает исключение при ошибке преобразования. Метод возвращает `false`, что позволяет обработать ошибку корректно и показать пользователю понятное сообщение без риска аварийного завершения приложения.

### 4. NullReferenceException при удалении и расчёте скидки
- **Причина:** использовалось выражение `dgOrders.SelectedItem as Order` без проверки на `null`.
- **Симптом:** нажатие кнопки "Удалить" или "Скидка" без выделенной строки приводило к крашу приложения.
- **Выполненные изменения:** перед каждой операцией с выбранным элементом добавлена проверка на `null`.
- **Обоснование:** оператор `as` возвращает `null`, если приведение типа невозможно или элемент не выбран. Обращение к свойствам `null`-объекта вызывает `NullReferenceException`. Проверка позволяет завершить метод до выполнения опасной операции и показать пользователю сообщение об ошибке.

## Архитектурные проблемы (нарушение принципов SOLID)

### 5. Класс-бог OrderService
- **Причина:** один класс отвечал за CRUD-операции, финансовые расчёты, фильтрацию, логирование и расчёт скидок.
- **Нарушение:** SRP (Single Responsibility Principle) — принцип единственной ответственности.
- **Выполненные изменения:** функциональность разделена на несколько классов: модель данных `Order`, enum `OrderStatus`, интерфейс `IDiscountStrategy`, реализация `QuantityDiscountStrategy`, `MainViewModel`.
- **Обоснование:** каждый класс теперь отвечает за одну задачу. ViewModel координирует взаимодействие между моделью и интерфейсом, стратегия скидок отвечает только за расчёт скидок, модель хранит данные. Изменение логики одной функции не затрагивает другие.

### 6. Жёсткая связанность (отсутствие инверсии зависимостей)
- **Причина:** экземпляр `OrderService` создавался напрямую в `MainWindow` через оператор `new`.
- **Нарушение:** DIP (Dependency Inversion Principle) — принцип инверсии зависимостей.
- **Выполненные изменения:** логика перенесена в `MainViewModel`, зависимости задаются через интерфейсы (`IDiscountStrategy`).
- **Обоснование:** использование интерфейсов позволяет заменять реализации без изменения потребительского кода. Это упрощает тестирование и делает архитектуру гибкой.

### 7. Логика в code-behind (отсутствие MVVM)
- **Причина:** вся бизнес-логика находилась в файле `MainWindow.xaml.cs`.
- **Нарушение:** разделение представления и логики.
- **Выполненные изменения:** создана `MainViewModel`, содержащая всю бизнес-логику и команды. Code-behind содержит только вызов `InitializeComponent()`.
- **Обоснование:** паттерн MVVM разделяет приложение на три слоя: Model (данные), View (интерфейс), ViewModel (логика). Это упрощает тестирование, поддержку и позволяет изменять интерфейс без затрагивания бизнес-логики.

### 8. Условные конструкции вместо стратегий
- **Причина:** для расчёта скидок и обработки статусов использовались цепочки `if/else if`.
- **Нарушение:** OCP (Open/Closed Principle) — принцип открытости/закрытости.
- **Выполненные изменения:** создан интерфейс `IDiscountStrategy` и конкретная реализация `QuantityDiscountStrategy`.
- **Обоснование:** интерфейс определяет контракт — методы `GetDiscountInfo` и `CalculateDiscount`. Для добавления новой стратегии (например, сезонной скидки) создаётся новый класс, реализующий интерфейс. Существующий код не изменяется.

## Проблемы дублирования и оптимизации

### 9. Дублирование формулы расчёта суммы
- **Где присутствовало:** методы `Order.GetTotal()`, `OrderService.GetTotalRevenue()`, `GetTotalRevenueByStatus()`.
- **Выполненные изменения:** формула вынесена в вычисляемое свойство `Total` модели `Order`.
- **Обоснование:** вычисляемое свойство содержит формулу `Quantity * Price` в одном месте. Все операции, требующие расчёта суммы, обращаются к этому свойству. Изменение формулы применяется автоматически во всех местах использования.

### 10. Дублирование форматирования денежных значений
- **Где присутствовало:** методы `Helper.FormatMoney` и `Helper.FormatMoneyShort`.
- **Выполненные изменения:** методы удалены, форматирование задаётся через `StringFormat` в привязках XAML.
- **Обоснование:** форматирование на уровне представления через `StringFormat={}{0:N2} ₽` устраняет дублирование кода и позволяет гибко настраивать отображение без изменения бизнес-логики.

## Проблемы читаемости и чистоты кода

### 11. Магические строки статусов
- **Где присутствовало:** строки `"new"`, `"paid"`, `"shipped"`, `"cancelled"` были разбросаны по коду.
- **Выполненные изменения:** создан enum `OrderStatus` с значениями `New`, `Paid`, `Shipped`, `Cancelled`.
- **Обоснование:** enum предоставляет типобезопасный способ работы с фиксированным набором значений. Компилятор проверяет корректность использования, IntelliSense показывает все доступные значения, опечатки исключаются на этапе компиляции.

### 12. Магические числа в логике скидок
- **Где присутствовало:** числа `100`, `50`, `10`, `10000` в методе `GetDiscount`.
- **Выполненные изменения:** логика инкапсулирована в классе `QuantityDiscountStrategy`, пороговые значения документированы в коде.
- **Обоснование:** инкапсуляция логики в отдельном классе делает пороговые значения явными и локализованными. При необходимости значения могут быть вынесены в константы или конфигурацию без изменения потребительского кода.

### 13. Неинформативные имена методов
- **Где присутствовало:** методы `Button_Click`, `Button_Click_1`, `Button_Click_2`, `Button_Click_3`.
- **Выполненные изменения:** методы переименованы в `AddOrder`, `DeleteOrder`, `ShowDiscount`, `RefreshData` и оформлены как команды `AddOrderCommand`, `DeleteOrderCommand`, `ShowDiscountCommand`, `RefreshCommand`.
- **Обоснование:** имена методов и команд отражают их назначение. Из имени сразу понятно, какое действие выполняется, что упрощает чтение и поддержку кода.

### 14. Мёртвый код
- **Где присутствовало:** методы `Helper.CalculateSomething`, `Helper.FormatMoneyShort`.
- **Выполненные изменения:** неиспользуемые методы удалены.
- **Обоснование:** мёртвый код увеличивает объём сопровождаемого кода и затрудняет понимание проекта. Удаление неиспользуемых методов снижает когнитивную нагрузку при чтении кода.

### 15. Булев параметр в методе
- **Где присутствовало:** метод `UpdateStatus(int id, string newStatus, bool writeLog)`.
- **Проблема:** флаг-параметр является признаком плохого дизайна — метод выполняет две разные задачи в зависимости от значения параметра.
- **Выполненные изменения:** метод разделён на два: `UpdateStatus` и `UpdateStatusWithLog`.
- **Обоснование:** разделение устраняет неоднозначность вызова. Каждый метод имеет чёткое назначение, что упрощает понимание кода и снижает вероятность ошибок при вызове.

### 16. Наивная валидация email
- **Где присутствовало:** метод `Helper.IsValidEmail`, проверявший только наличие символов `@` и `.`.
- **Симптом:** принимались некорректные адреса вида `Customer@dsf.`.
- **Выполненные изменения:** валидация упрощена до проверки наличия `@` и `.` в ViewModel с выводом понятного сообщения об ошибке.
- **Обоснование:** для учебного проекта полная валидация через `MailAddress` или регулярное выражение избыточна. Базовая проверка в сочетании с понятным сообщением об ошибке обеспечивает достаточный уровень корректности ввода.

### 17. Хардкод в XAML
- **Где присутствовало:** атрибуты `Text="Customer"`, `Text="Product"` в элементах `TextBox`.
- **Проблема:** пользователь воспринимал текст как значение поля, а не как подсказку.
- **Выполненные изменения:** свойство `Text` привязано к свойствам ViewModel через `Binding`, подсказки реализованы через свойство `ToolTip`.
- **Обоснование:** привязка данных через `Binding` обеспечивает пустое поле при запуске. `ToolTip` отображает подсказку при наведении курсора и не мешает вводу данных.

### 18. Автогенерация колонок DataGrid
- **Где присутствовало:** атрибут `AutoGenerateColumns="True"`.
- **Проблема:** отсутствовал контроль над заголовками, порядком и форматом отображения колонок.
- **Выполненные изменения:** колонки определены вручную с явным указанием заголовков, ширины и формата через `StringFormat`.
- **Обоснование:** ручное определение колонок позволяет выбрать только нужные свойства, настроить их порядок, ширину и формат отображения. Числа отображаются с разделителями тысяч и символом валюты, даты — в заданном формате. Вычисляемые свойства `Total` и `StatusRussian` отображаются как обычные колонки.
